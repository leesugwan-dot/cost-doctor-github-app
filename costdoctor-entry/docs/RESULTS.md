# 결과 읽기와 Before/After

`SCAN_COMPLETE`는 정해진 파일/크기 범위의 스캔이 끝났다는 뜻입니다. 제품·절감·품질 PASS가 아닙니다. `PARTIAL_SCAN`이면 제외된 링크·큰 파일·읽기 오류·한도를 먼저 확인합니다. `NO_MATCH_IN_SCANNED_SCOPE`도 낭비가 없다는 뜻이 아닙니다.

4개 항목은 기존 공개 App의 검토 분류를 이어받은 로컬 정적 신호입니다. 예제·주석·테스트에도 나타날 수 있습니다. 먼저 신호가 많은 항목 하나를 고르고 실제 반복 실행을 관측하세요. 신호가 있다는 이유만으로 캐시/재시도를 삭제하지 마세요.

실제 개선 확인 순서:

어디에서 확인할지 모르겠다면 GitHub 저장소의 코드 검색에서 모델 호출은 `chat(` 또는 `generate(`, 재시도는 `retry`, 캐시는 `cache`, 문맥은 `num_ctx` 또는 `max_tokens`를 검색하세요. 이는 고정 검색어 안내이며 도구가 파일 위치나 실제 낭비를 증명했다는 뜻이 아닙니다. 검색된 항목이 예제·테스트인지 먼저 확인하세요. 코드를 직접 판단하기 어렵다면 보고서의 항목명과 질문만 저장소 관리자에게 전달하고 임의 수정하지 마세요.

1. 같은 목표, 입력, commit, 모델/provider, 품질 기준, 재작업 정의를 고정합니다.
2. Before에서 실제 사용량·호출·시간·실패/재시도를 기록합니다. 비밀키·프롬프트·원문 로그는 제출하지 않습니다.
3. 별도 branch/격리 사본에 개선을 적용합니다. rollback할 원래 commit을 보존합니다.
4. 동일 조건 After와 품질·오탐·실패·재작업을 비교합니다. 진단/검증 자체의 비용도 포함합니다.
5. 실제 usage와 검증된 가격/청구 출처가 모두 있을 때만 금액을 계산합니다. 그렇지 않으면 UNKNOWN입니다.
6. 품질 악화·오탐 증가·재작업 증가가 있으면 성공으로 표시하지 않고 해당 개선을 되돌립니다.

기존 CostDoctor scan/optimize/verify/guard 제품과 인증 경계는 그대로입니다. 이 entry candidate는 새 자동 금액 verifier를 만들지 않습니다. 기존 제품을 보유한 소유자는 그 제품의 exact 사용량/작업명세/영수증 결속 절차를 사용할 수 있지만, 비공개 제품 코어를 이 Action에 번들하거나 외부 사용자에게 임의 배포하지 않습니다.

이전 공개 OSS 시간 개선과 두 API workload 결과는 과거 제한 범위입니다. 새 저장소 결과나 모든 고객의 평균 절감률이 아닙니다.
